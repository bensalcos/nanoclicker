# Performance experiment ledger

Keep the original budgets in VALIDATION.md. A reduction in one internal cost does not close a whole-application or native-platform gate.

| Attempt | Evidence | Decision |
|---|---|---|
| Progress snapshots at 2 Hz instead of 10 Hz | Whole GUI active CPU fell from 19.67% to about 5.23% on software X11; immediate first pair and lifecycle transitions retained | Kept in b0d52d8; CPU/RAM still exceeded targets |
| Reduce progress snapshots from 2 Hz to 1 Hz | Two full 2 Hz release/X11 controls measured 4.6998%/4.9831% active CPU; two 1 Hz candidate trials measured 2.8165%/2.9833%. All four captured 6001 pairs; p99/max interval error was 0/1 ms in each 1 Hz trial and in the second 2 Hz trial. Idle RSS ranged 107.059–107.301 MiB. Two 10 s quick candidate samples were 2.60% and 2.80%, with exact 1001-pair captures. See [UI polish performance](ui-polish-performance.md). | Keep 1 Hz provisionally: both matched full trials show about 40% lower active CPU with exact receipt and similar startup/RSS. Confirm once-per-second progress feedback usability before acceptance; software RSS remains above target. |
| Current-source 1 Hz renderer comparison | Two full WGPU/lavapipe runs measured 3.2998%/3.4998% CPU and 106.141/105.945 MiB idle RSS, each with 6001 pairs. Matched Glow runs measured 2.8165%/2.9833% CPU and 107.309/107.059 MiB RSS. Two additional full trials per renderer on AMD Renoir/RADV measured mean WGPU startup p95 53.284 ms and idle RSS 58.827 MiB, versus Glow 112.062 ms and 83.084 MiB; active CPU was near equal and all trials captured 6001 pairs. See [software comparison](renderer-comparison.md#current-source-1-hz-follow-up--2026-10-25) and [GPU comparison](gpu-renderers.md#current-source-1-hz-gpu-follow-up--2026-10-26). | Set WGPU as provisional Linux default based on repeated GPU startup/memory results; retain Glow as a build-time compatibility option. Do not treat the software CPU/RSS excess or native compatibility, accessibility and backend gates as accepted. |
| Limit glibc arenas with `MALLOC_ARENA_MAX=1` | One 10-second quick profile per configuration on the same WGPU/lavapipe release binary (`2cab232157fc957bbfaceca1909f9816ab0ed9c47d28ea110b6cded435828031`) measured idle RSS 105.258 MiB normally and 104.832 MiB with the limit. Both captured 1001 pairs; active CPU was 3.5986% and 3.4985%, respectively. | Reject as a product launch setting: the exploratory 0.426 MiB reduction leaves RSS over 100 MiB and is not a repeated full-profile result. See [software-renderer memory triage](ui-polish-performance.md#software-renderer-memory-triage--2026-10-26). |
| glibc trim-threshold tunable | One valid 10-second repeat with `GLIBC_TUNABLES=glibc.malloc.trim_threshold=0` measured 104.719 MiB idle RSS, 104.871 MiB active RSS and 3.5986% active CPU, with 1001 pairs; one earlier attempt exited before active sampling and was discarded. | Reject as a product setting: the single valid sample is only about 0.54 MiB below the matching 105.258 MiB baseline and remains above 100 MiB. See [software-renderer memory triage](ui-polish-performance.md#glibc-trim-threshold-probe--2026-10-26). |
| LLVMpipe worker count on WGPU OpenGL software | One 10-second `LP_NUM_THREADS=1` quick profile measured 117.105 MiB idle RSS, 2.8986% CPU and 1000 pairs versus the earlier 117.746 MiB/4.2992%/1001-pair sample. | Reject as a product setting: the single unmatched sample saves 0.641 MiB but remains far above the RSS budget. This Gallium setting does not apply to the Vulkan/lavapipe default. See [LLVMpipe probe](ui-polish-performance.md#llvmpipe-worker-count-probe--2026-10-26). |
| Linux WGPU GLES feature removal | Vulkan-only candidate compiled and passed isolated X11 GUI acceptance; release executable is 3,590,424 bytes (2.49%) smaller. One quick sample measured 109.980 MiB idle RSS and 3.5994% CPU with 1001 pairs. | Provisional only: the software RSS target remains unmet, the historical 105.258 MiB baseline is not a matched comparison, and systems without Vulkan need the Glow package. Repeat matched profiles and validate current source in the Windows VM before deciding. See [Vulkan-only WGPU feature probe](ui-polish-performance.md#vulkan-only-wgpu-feature-probe--2026-10-26). |
| Renderer feature isolation | Removed the unconditional Linux eframe WGPU feature so the documented Glow build no longer compiles WGPU. The current-source Windows VM and native Linux acceptance remain open. See [renderer feature-isolation follow-up](ui-polish-performance.md#renderer-feature-isolation-follow-up--2026-10-26). |
| WGPU OpenGL software backend | One 10-second quick profile with `WGPU_BACKEND=gl` measured 117.746 MiB idle RSS, 4.2992% active CPU and 1001 captured pairs; the matching Vulkan/lavapipe profile measured 105.258 MiB, 3.5986% and 1001 pairs. | Reject for software rendering: it adds 12.488 MiB idle RSS and does not improve CPU or pair delivery. See [software-renderer memory triage](ui-polish-performance.md#software-renderer-memory-triage--2026-10-26). |
| Use `/proc/PID/io` syscr/syscw as native X11 send counts | 1001 pairs reported only 770 write-family calls; x11rb uses sendmsg, which these counters do not fully represent | Rejected as a socket-send metric; temporary counter code removed |
| Read per-mapping RSS | [Mapping sample](idle-mappings-baseline.csv): LLVM about 46.7 MiB, application executable about 10.9 MiB; 10-second stabilization is exploratory | Kept in the isolated harness, outside measured CPU windows; full RSS budget still uses 60-second runs |
| Remove explicit flush before checked X11 cookies | [Two native traces per build](x11-flush-optimization.md) save about one sendmsg and one ppoll per complete pair; both error checks and recovery retained | Kept after tests and real release GUI verification; no total-CPU claim from traced runs |
| Cross-crate ThinLTO for mapped-code/RSS reduction | [Matched quick screening](thin-lto-experiment.md): only 16 KiB RSS difference, ELF grows 89,928 bytes; no CPU gain established | Rejected; Cargo profile unchanged, experiment recorded |

The mapping sample uses Mesa 26.2.2 and LLVM 22.1.8. Shared executable/library pages contribute to RSS; do not substitute PSS or private memory for the existing RSS target. The software driver dominates the current footprint, but the application's own mapped code is still a valid candidate for measured release-build optimization. Do not remove accessibility, fonts, backends or checks merely to make a number pass.
