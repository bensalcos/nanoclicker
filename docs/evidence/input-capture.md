# Passive native input capture target

The `nanoclick` package now has an `input_capture` example for the required native capture work. Its safe Rust code only receives its own window events. It neither calls the injection adapters nor requests portal control. The actual raw display-handle variant attests Windows/X11/Wayland; environment variables alone are not used as native-backend proof. `raw-window-handle` is an example-only dev dependency already present at the same locked version through eframe; no package/version was added and normal production dependency selection is unchanged.

The target requires a new output file, remains unarmed until Space and writes only metadata/session summaries. It tracks five distinct pointer buttons in fixed space, duplicate/unmatched/overlapping presses, held buttons and overflow. New sessions require all observed buttons released. Escape/ordinary window close saves an active session exactly once. Output failure remains visible, prevents a new session and produces a nonzero exit after closing. No per-event file I/O or raw key/pointer/device logging is added to the producer.

Nine unit tests pass: armed-only routing, malformed sequences, held-state start rejection, session reset, cross-button overlap, extra-button distinction, overflow, no-clobber/private output and writer errors. Five accounting tests failed in the initial stub before implementation. [Unit output](input-capture-unit.txt). The workspace all-targets run passes 60 Rust tests: the existing 51 plus nine capture tests. Windows MSVC cross-target Clippy, Linux feature/wgpu Clippy and Rust 1.95 example checking pass.

A private authenticated Xvfb drives the actual release target at synthetic 200% scale. It verifies backend metadata, ignored pre-arming input, exact separate 3-left/5-right/7-middle sessions, fresh identities/counters, balanced state and one saved active-close session before clean exit. [Window output](input-capture-window.txt). Release target SHA-256: `56ec0cc2062fd17e243e1b6abb04f5a58070caedf8d73743694edfaf75392434`. The generic window helpers were separated from NanoClick-specific action/discovery logic; the existing product GUI/finite/preferences flow still passes after that refactor.

This is target validation on Xvfb, not native Windows or Wayland acceptance. GUI event processing can batch timestamps and toolkit state is not global physical button state; summaries do not accept timing budgets, monitor transitions or screen readers. Use the [native QA protocol](../NATIVE_QA.md) for manual desktop runs. A licensed downloadable Windows capture-tool bundle is not prepared yet; the example can be built from source. Hosted checks for the new target are pending.
